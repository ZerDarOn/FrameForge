# FrameForge - AI动画帧审查工具

**设计文档**
**日期：** 2026-06-09
**状态：** 已确认

---

## 1. 概述

FrameForge 是一款桌面应用程序，用于审查、对齐和质量检测 AI 生成的动画帧序列。它提供基于时间线的工作流，并结合 AI 辅助分析，用于检测帧间的位移、闪烁和角色不一致问题。

### 问题背景

AI 动画工具（Runway、Kling、Midjourney 等）生成的是独立的片段或帧，但缺乏专门的审查和校正工具。创作者目前只能依赖传统的非线性编辑器（After Effects、Premiere Pro）来拼接和检查帧序列——这种工作流并非为 AI 生成的素材而设计。FrameForge 填补了这一空白，提供专用的帧级检查和 AI 辅助对齐功能。

### 目标用户

独立的 AI 动画创作者，需要：
- 在时间线上组织 AI 生成的图片序列和视频片段
- 以参考点为基准检查帧间对齐情况
- 检测并修复位移、闪烁和不一致问题
- 预览并导出最终动画

## 2. 架构

### 2.1 技术栈

| 层级 | 技术选型 | 理由 |
|------|---------|------|
| 桌面框架 | Tauri v2 | 轻量（~5MB）、安全、Rust 后端高性能 |
| 前端框架 | React 18 + TypeScript | 生态成熟，类型安全 |
| 2D 渲染 | PixiJS v8 (WebGL) | Sprite 批处理、纹理管理、高性能 2D |
| 3D 扩展 | Three.js（预留） | 未来 3D 预览能力 |
| 状态管理 | Zustand | 轻量、TypeScript 友好 |
| 样式 | TailwindCSS | 快速开发、一致性 |
| 后端 | Rust | 图像处理、AI 推理、文件系统操作 |
| 本地 AI | ONNX Runtime (Rust bindings) | 轻量推理，实时检测 |
| 云端 AI | OpenAI API / 自部署模型 | 复杂分析（一致性检查、建议生成） |
| 图像处理 | Rust `image` crate + `opencv-rust` | 高性能像素操作 |
| 视频处理 | `ffmpeg-next` (Rust) | 帧提取、编码、导出 |
| 项目存储 | SQLite (`rusqlite`) | 项目元数据、分析结果 |

### 3.1 核心交互流程

**流程 1：项目创建与资产导入**
1. 创建项目，设定帧率（12/24/30fps）和画布尺寸
2. 拖拽导入图片序列帧（支持 PNG/JPG/WebP 文件夹批量导入）
3. 导入视频片段（MP4/WebM，自动提取帧）
4. 资产自动分配到轨道，支持手动拖拽重排

**流程 2：基准点设定**
1. 在任意帧上点击设定基准点（如角色眼睛位置、地平线等）
2. 基准点可以是：点、线、或区域
3. 支持多个基准点（不同类型的对齐参考）

**流程 3：逐帧审查**
1. 拖拽时间线播放头逐帧浏览
2. 开启洋葱皮叠加前后帧对比
3. 放大镜工具检查像素级细节
4. AI 检测结果叠加在画面上（位移箭头、闪烁高亮、不一致区域标记）

**流程 4：AI 分析**
1. 一键启动全序列 AI 分析
2. 分析结果在时间线上以彩色标记显示问题帧
3. 右侧面板显示详细分析报告
4. AI 给出修复建议（如"建议将第45帧向右偏移 2px"）

**流程 5：自动对齐**
1. 选择基准点后，一键对齐所有帧
2. 支持手动微调 AI 建议的偏移量
3. 对比视图：对齐前/对齐后

**流程 6：展示空间**
1. 全屏预览模式，干净的播放体验
2. 支持导出为 GIF/MP4/WebP
3. 未来：可分享链接

## 4. 数据模型

```

├── total_frames, issues_found
├── displacement_map[] (帧间位移数据)
├── flicker_report[] (闪烁帧列表)

```

## 5. AI 分析能力

### 5.1 本地 AI（ONNX Runtime）

| 功能 | 算法 | 输入 | 输出 |
|------|------|------|------|
| 帧间位移检测 | 光流法 (Farneback) + 相位相关 | 相邻帧对 | 位移向量 (dx, dy) |
| 闪烁检测 | 帧间 SSIM + 直方图差异 | 相邻帧对 | 闪烁分数 + 问题帧列表 |
| 基准点追踪 | KLT 特征追踪 | 基准点坐标 + 帧序列 | 各帧基准点位置 |

### 5.2 云端 AI（API 调用）

| 功能 | 模型 | 输入 | 输出 |
|------|------|------|------|
| 角色一致性检查 | 多模态 LLM (GPT-4V 等) | 连续帧截图 | 一致性评分 + 差异描述 |
| AI 建议生成 | LLM | 问题帧 + 检测结果 | 修复建议（自然语言） |
| 背景一致性 | 多模态 LLM | 背景区域截图 | 一致性评分 |

### 5.3 AI 分析结果可视化

```
时间线上的标记：
  红色 = 高严重度问题（位移 >3px / 严重闪烁 / 角色突变）
  黄色 = 中等严重度（位移 1-3px / 轻微闪烁）
  绿色 = 通过（无显著问题）

画面叠加层：
  - 位移：红色箭头显示偏移方向和距离
  - 闪烁：蓝色半透明高亮闪烁区域
  - 不一致：黄色边框标记差异区域
```

## 6. 架构决策记录

### ADR-1：渲染引擎选择
- **决策：** 使用 PixiJS v8 作为 2D WebGL 渲染引擎，预留 Three.js 接口
- **背景：** 需要高性能渲染大量帧缩略图 + 实时预览
- **备选方案：** PixiJS / Konva.js / 原生 Canvas
- **选择：** PixiJS — 成熟的 WebGL 2D 引擎，内置 Sprite 批处理和纹理管理
- **取舍：** 增加 ~300KB 依赖，但换来自动批处理和纹理池管理
- **回退方案：** 可退回原生 Canvas API

### ADR-2：AI 推理策略
- **决策：** 混合推理 — 本地 ONNX Runtime 做轻量检测，云端 API 做复杂分析
- **背景：** 位移/闪烁检测需要实时性，一致性检查需要强模型
- **备选方案：** 全本地 / 全云端 / 混合
- **选择：** 混合 — 本地做 SSIM/光流/像素差异，云端做多模态分析 + 建议生成
- **取舍：** 高级 AI 功能需要网络连接，但本地基础功能不受影响
- **回退方案：** 可切换为全本地模式（降低 AI 精度）

### ADR-3：桌面框架选择
- **决策：** Tauri v2 而非 Electron
- **背景：** 需要原生文件系统访问、图像处理性能、小安装包
- **备选方案：** Tauri / Electron / Neutralino
- **选择：** Tauri — Rust 后端处理性能关键任务，~5MB 安装包 vs Electron ~150MB
- **取舍：** 社区比 Electron 小，Rust 学习曲线
- **回退方案：** 如果 Tauri 限制成为阻碍，可以迁移到 Electron

### ADR-4：项目存储方案
- **决策：** SQLite 存储元数据，文件系统存储资产
- **背景：** 需要对项目数据进行结构化查询，但资产是大体积二进制文件
- **备选方案：** 仅 SQLite / JSON 文件 / SQLite + 文件系统
- **选择：** SQLite + 文件系统 — 元数据入库便于快速查询，资产保留原始文件
- **取舍：** 需要管理文件路径一致性
- **回退方案：** 可迁移到基于 JSON 的存储方案

## 7. 构建顺序

```
Tauri 壳 → 资产管理器 → 时间线引擎 → 帧检查器 → AI 分析器 → 对齐引擎 → 展示空间
```

- 阶段 1（MVP）：Tauri 壳 + 资产管理器 + 时间线引擎 + 帧检查器
- 阶段 2：AI 分析器 + 对齐引擎
- 阶段 3：展示空间 + 导出功能
- 阶段 4（未来）：云端 AI 集成、生成端接入、团队协作

---

## 8. 关键假设

1. 用户主要处理 2D 帧（PNG/JPG 序列），视频片段为辅
2. 帧数量级在 100-5000 帧/项目
3. 用户机器有独立 GPU（WebGL 所需）
4. 用户接受本地基础 AI 功能 + 在线高级功能的模式
5. 初始版本不集成生成端（预留接口）
